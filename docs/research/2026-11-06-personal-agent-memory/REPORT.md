# Morgan как персональный агент 24/7

Исследование на 6 ноября 2026 года. Статус: проработка, без внедрения.

## Вывод для Morgan

Конечная цель Morgan — персональный агент, доступный 24/7, который помнит контекст владельца, ведёт задачи, по делу проявляет инициативу и остаётся управляемым. Независимая долговечная память и сменяемые Codex, Claude Code или локальные модели — средства для этой цели, а не отдельный конечный продукт. Надёжный архив исходных сообщений нужен рядом с runtime задач, контролем действий и доставкой результатов.

Это продолжение существующего направления Morgan. В найденной локальной копии уже есть SQLite, общий MemoryGate, CLI/MCP, происхождение записей, исправления и точное чтение источников без модели. Однако универсальный захват истории Codex/Claude Code не обнаружен, а основной ranked recall зависит от embedder. Требование «никакого обязательного inference в архиве и поиске» ещё нельзя считать полностью выполненным.

Для памяти ближайшие ориентиры — CASS и sessionwiki; для постоянного агента — OpenClaw, nanobot и актуальный Letta Code. Предпочтительное направление проработки: выбрать сменяемый runtime для задач и каналов, сохранив Morgan владельцем памяти и пользовательской политики. Возвращать старый kernel целиком без проверки готовых runtime оснований нет. Но ограничение текущего ROADMAP «No assistant» больше не выражает продуктовую цель владельца: оно описывает лишь нынешний объём реализации.

## Предлагаемый минимальный контракт

Ниже — предложение для следующего этапа, не описание реализованных функций.

```text
Сохранённая история Codex / Claude Code / другого клиента
                         ↓
             adapter конкретного формата
                         ↓
        единый reader и фильтр допустимых событий
               ↙                     ↘
    вызов после live-сигнала       ручной backfill
               ↘                     ↙
       MemoryGate → долговечные записи SQLite
                         ↓
          FTS5 → короткие результаты с ID
                         ↓
       точное чтение выбранного текста и соседних реплик
                         ↓
         любой внешний harness интерпретирует ответ
```

**Захват.** Hook лишь сообщает, что сохранённую историю стоит перечитать. Содержимое hook payload не становится второй реализацией импорта. Reader один на формат и общий для live/backfill. Документация [Claude Code hooks](https://code.claude.com/docs/en/hooks) предоставляет transcript_path, но наличие пути не доказывает, что последняя запись уже полностью сброшена на диск: допускаются повторное чтение и задержка.

**Состав.** Сохранять буквальный текст явного пользовательского ввода и законченного ответа, роль, время источника, время поступления, client, project/owner, session/message identity и доступный locator. Нормализация для поиска не меняет оригинал. Форматы событий различаются: role=user может включать не набранный пользователем текст, а role=assistant — промежуточные сообщения. Неизвестные типы следует пропускать с диагностикой, а не молча объявлять final. Финальность проверяется адаптером по документированным признакам формата и fixtures. Ни reasoning, ни tools, ни commentary, ни subagent chat, ни compaction-summary не подменяют оригинальные реплики.

**Повторы и ветки.** Идентичное событие не дублируется при backfill; ключ включает namespace клиента и сессии, а не один content hash. Одинаковая фраза в двух разных разговорах остаётся двумя событиями. Изменившееся содержимое под тем же ID не должно перезаписывать старую историю без следа. Parent/branch указываются только при наличии в источнике. Нельзя объединять все ветки в один якобы последовательный разговор или угадывать старую ancestry по похожему тексту.

**Сохранность.** Скопированные допустимые сообщения — durable данные, FTS — перестраиваемая производная. Исчезновение исходного файла не запускает каскадное удаление архива. Cursor продвижения и принятые строки фиксируются атомарно; неполная JSONL-строка не считается успешно обработанной. Простого повторного сканирования достаточно, пока измерения не покажут необходимость более сложного курсора. При смене parser сохраняется версия и понятная процедура повторного чтения, без разрушительного rebuild canonical текста.

**Границы гарантий.** Best-effort не значит «никогда ничего не теряется»: сообщения, удалённые до первого успешного чтения, восстановить нельзя. Отдельный SQLite на том же диске не защищает от потери диска. Для резервирования подходят SQLite Online Backup API или VACUUM INTO; восстановление нужно проверять отдельно. [Документация SQLite](https://www.sqlite.org/backup.html).

**Поиск.** Начать с FTS5, фильтров scope/client/дата и ограниченных результатов с ID. `unicode61` понимает Unicode-токены, но не обеспечивает русскую морфологию или семантические парафразы. Trigram полезен для подстрок, но имеет свои ограничения. В первом сравнении оценить оба режима на реальных вопросах; не добавлять embeddings до доказанного провала lexical baseline. [FTS5](https://www.sqlite.org/fts5.html).

**Progressive disclosure.** В doc tree — краткое описание возможностей и границ. При поиске — несколько ID, время, роль, scope и короткий фрагмент. Затем агент запрашивает нужные записи или ограниченное окно соседних допустимых сообщений. Не отправлять весь архив в prompt. Если найден лишь фрагмент без необходимых соседей, это явно неполное свидетельство.

**Интеграция в Morgan.** Предпочтение — логически отдельный слой исходных разговоров в существующем хранилище и через существующий gate. Отдельный SQLite-файл допустим как изолированный исследовательский артефакт, но постоянная вторая база создаст второй контракт backup/forget и требует обоснования. Не стоит бездумно пропускать каждую реплику через текущий store с обязательным embedding и семантической консолидацией. Финальное решение по схеме принимается после проверки малого ingestion-примера, не в этом исследовании.

## Приватность и границы доверия

Локальное хранение не равно локальному использованию: если облачный агент читает найденную цитату, она уходит в его контекст. Scope и разрешение на передачу нужно применять до выдачи snippet и до внешнего embedding. MCP-клиентам нужна явная аутентификация там, где есть сетевой доступ; поля client/author сами не аутентифицируют отправителя.

Область захвата задаётся явно, с исключением приватных/рабочих проектов по политике владельца. Сырые transcripts не следует целиком дублировать ради удобства: они могут содержать именно те tool outputs и внутренние сообщения, которые пользователь исключил. Canonical архив здесь означает сохранённый разрешённый текст, а не все байты исходного файла.

Чтение старой инструкции не разрешает её исполнение. Сохранённые реплики и найденные статьи — данные с provenance; они не могут отключать текущие ограничения, разрешать новые действия или автоматически считаться актуальной истиной. Morgan уже выражает это через `action_authority: none` в continuation-контракте.

Долговечность должна сочетаться с явным forget. Нужно определиться, удаляется ли только индексированная копия либо также разрешённые источники/экспорты; без этого повторный backfill может вернуть удалённое. Если исходники сохраняются, нужен минимальный механизм исключения повторного импорта удалённой области. Он защищает конкретное требование, а не строит универсальный compliance-сервис. Snapshots и внешние экспорты требуют отдельной политики: существующий forget не может отозвать уже отправленный текст.

## Персональный агент 24/7 и выбор runtime

24/7 означает доступность, устойчивость состояния и своевременное выполнение разрешённых задач. Постоянный поток LLM-вызовов не нужен. Агент может спать между событиями, просыпаться по расписанию, хранить незавершённые поручения и объяснять задержки. Память разговоров обеспечивает контекст, но не заменяет реестр задач, supervisor процесса и статус доставки.

В найденной копии Morgan такой runtime отсутствует по заявленному текущему объёму. Архивный Personal Agent OS vision от 09.06.2026 описывает более широкие возможности, но его же статус помечен superseded, а новые документы явно ограничивают ядро. Это не повод объявлять задачу 24/7 решённой после добавления SQLite index.

У OpenClaw в проверенной версии heartbeat уже мигрирует в обычные automation jobs; старые инструкции с отдельным heartbeat-контуром могут быть неверны. Поэтому нельзя просто скопировать популярный HEARTBEAT.md-рецепт и считать его контрактом постоянной работы.

У nanobot [документированы состояния доставки](https://github.com/HKUDS/nanobot/blob/92e6608e6e6cbd0324d18d214932a03a7efa11be/docs/automations.md): сохранённый результат, очередь, попытка отправки и неизвестный исход различаются; неизвестная отправка не повторяется автоматически. Его [deployment guide](https://github.com/HKUDS/nanobot/blob/92e6608e6e6cbd0324d18d214932a03a7efa11be/docs/deployment.md) отдельно рассматривает OS-managed service. Это полезные контракты для Morgan, а не подтверждение их работы в нашей среде.

### Рекомендуемые границы компонентов

Предлагается единая личность Morgan и единый интерфейс задач для владельца. Внутри runtime отвечает за запуск работы, расписания и каналы; существующее ядро Morgan — за долговечные источники, provenance и scoped retrieval; модели и coding harness — за отдельные ограниченные запуски. Пользовательская политика определяет доступные инструменты, пределы расходов и действия, требующие подтверждения. Не создавать второй competing scheduler внутри memory core, если выбранный runtime уже выполняет эту функцию.

Нужны два вида состояния: «что обсуждалось» и «что сейчас исполняется». В журнале разговоров фраза «сделал» остаётся высказыванием ассистента. Завершение задачи устанавливается проверяемым результатом: существующим артефактом, ответом API, выполненным тестом. Отправленное сообщение и подтверждённая доставка также не смешиваются.

Минимальный жизненный цикл поручения: queued → running → succeeded / failed / blocked / cancelled; отдельно unknown для внешнего эффекта с неопределённым исходом. После перезапуска безопасный read-only шаг можно повторить, отправку или изменение во внешней системе — сначала сверить с destination или idempotency key. Идентичность task/run/action хранится до выполнения эффекта. На старте достаточно одного активного исполнения на область пользователя/проекта и ограниченного числа параллельных задач; распределённый scheduler не нужен.

### Надёжность и наблюдаемость

- Supervisor ОС следит за процессом, но не объявляет задачу выполненной. На Mac требуется отдельно проверить sleep, logout, reboot и сеть; «ноутбук включён» не является гарантией своевременных запусков. Ни sleep settings, ни LaunchAgent сейчас не менялись.
- Разделять liveness процесса, доступность БД, доступность модели и работоспособность канала. Локальная память должна читаться при outage модели; задачи получают видимый blocked/degraded статус.
- После сбоя возобновлять только безопасные шаги. Для пропущенного расписания заранее определить skip/catch-up/latest-only, timezone и DST; не выполнять все пропуски пачкой по умолчанию.
- Ограничить task timeout, число шагов, retries, одновременные задачи и дневной бюджет. Для повторных отказов provider использовать паузу с понятным статусом; не переключать автоматически на внешний provider при запрете egress.
- Метрики владельцу: последняя успешная полезная задача, очередь, длительно running/blocked, возраст последнего backup, доступность канала, расходы. Не логировать полные личные сообщения и секреты ради мониторинга.
- Backup должен охватывать память и runtime task/outbox state с понятной точкой согласованности. Восстановление БД Morgan на работающем сервере запрещено его текущим OPERATIONS.md: менять файл под открытыми соединениями опасно.

### Проактивность и контроль

Начальный полезный набор сценариев: продолжить прерванную исследовательскую задачу; найти прежнее решение и показать источник; составить утреннюю сводку по выбранным источникам; предупредить о конкретной просроченной задаче. Это кандидаты для приёмки, не созданные расписания.

Периодическая проверка должна молчать, если нет существенного изменения. Для уведомлений нужны quiet hours, дедупликация, cooldown и объяснение «почему я сейчас сообщаю об этом». Повторяющийся шум — дефект продукта. Внешние сообщения, покупки, удаления и расширение доступа управляются конкретной политикой владельца; старый текст в памяти не является новым согласием.

Доступные человеку команды: статус, список задач, pause/resume, cancel конкретной задачи, остановить все новые исполнения, отозвать connector, посмотреть действия и расходы, забыть область. Pause не должен обещать отменить уже совершённый эффект. Отзыв разрешения проверяется непосредственно перед следующим действием, а не только при создании поручения.

### Как выбирать без преждевременной переписки

Первым проверить nanobot и OpenClaw в одинаковом изолированном сценарии; Letta оставить третьим вариантом, если важны его stateful identity и memory-workflows. Это исследовательский приоритет, не окончательный выбор победителя. Сравнение должно включать restart до/после side effect, provider outage, duplicate event, missed schedule, отмену, revocation, канал с timeout и чтение источника из Morgan через gate.

Перед включением реального 24/7 режима провести ограниченный shadow run на синтетических задачах без отправки сообщений и внешних изменений. Условия приёмки: нет потерянных поручений, двойных внешних эффектов, выхода за scope/бюджет; неопределённые результаты видны; после stop работа не продолжается; расписание не изображает точность, которую хост обеспечить не может. Длительный запуск и production подключение в этой задаче не выполнялись.

## Что остаётся неподтверждённым

Заявления из присланных постов о BitGN, переносе тренировки между агентами, высказываниях Tibo и экономии Revolut примерно 90% не сопровождались первичными ссылками и не используются как доказательство архитектурного решения. Фраза «разговоры не теряются» — желаемое свойство, а не установленная гарантия SQLite или конкретного hook.

Не проверено, удовлетворяет ли какой-либо готовый репозиторий всему строгому final-only контракту на установленной у владельца версии клиентов. Не проверялось актуальное развёртывание Morgan и не выполнялись benchmark/live-model вызовы. Для полноценного результата 24/7 ещё требуются выбор runtime, интеграционный recovery-тест и отдельное решение о постоянном запуске. Проверенные контракты хранения позволяют опереться на существующее ядро, но не заменяют эти шаги.

## Формулировка для идеи Morgan

> Morgan — персональный агент, который работает 24/7, помнит владельца и его проекты, ведёт поручения и проявляет полезную инициативу в заданных границах. Его память принадлежит пользователю и переживает смену моделей и агентских оболочек. Исходные сообщения сохраняются с происхождением; базовый поиск не требует LLM. Надёжный runtime восстанавливает задачи после сбоев, различает выполненную работу и доставленный результат и не повторяет сомнительные внешние действия вслепую. Пользователь видит, что происходит, может ограничить расходы, приостановить работу и отозвать доступ.
